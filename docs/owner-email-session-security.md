# Owner email-session security

Owner email-code access requires the existing admin row whose exact OAuth subject hashes to the server-side SHA-256 allowlist and whose normalized recovery email matches the independently authorized server-side pin `belllo.ayoola@gmail.com`. The pins are identifiers, not secrets; an email match alone never confers ownership. When `OWNER_OPEN_ID` is nonempty, its exact bytes must hash to the subject pin and the returned DB subject must exactly equal it; a conflicting or malformed value fails closed. With the setting absent or empty, the resolver hashes all admin subjects and requires exactly one matching eligible row. A changed or missing DB recovery address fails closed for code issuance, verification and marked sessions, even if a fingerprint matches the changed address. This design introduces no schema, migration, runtime binding write, or email-code owner promotion. Changing either pin requires a reviewed code change and deployment.

A newly issued marked email-OTP session carries an HMAC of the exact subject and normalized email, not the email itself or the presence of an environment variable. Each request re-resolves the pinned subject and checks the existing user's admin role and email. Normalization ignores email case and surrounding whitespace. Restoring the same valid `OWNER_OPEN_ID` after it was absent does not invalidate the session. A conflicting setting blocks it until corrected.

**Legacy sessions:** Marked tokens without the fingerprint are rejected. Tokens produced by the prior uncommitted binding-based fingerprint, which included configuration-source flags, are incompatible and must be reissued. Unmarked older sessions follow the existing ordinary authentication path and do not gain these checks; audit or revoke them separately. Neither this change nor these checks provide universal session revocation.

**Restoration limitation:** The fingerprint checks current state, not history. An unexpired marked session can work again if the original pinned subject, normalized email, and admin role are restored after demotion, deletion, an email change, or a configuration conflict. Permanent revocation across restoration needs a durable monotonic authentication generation, updated transactionally by every relevant lifecycle path; none is introduced here.

**Public resend availability tradeoff:** A successful issuance after the 60-second cooldown retires all prior unconsumed codes for that address; verification considers only the newest challenge, even if delivery failed or it is consumed. This prevents revival of older codes but permits anyone who knows an eligible address to repeatedly request new codes and disrupt sign-in after each cooldown. A delivery failure also revokes the newly issued code and does not restore the prior one. The generic response and cooldown limit disclosure and frequency, not this availability risk; account-level abuse defenses require separate design and review.

Existing configured-owner inserts still receive the admin role. Ordinary upsert of an existing configured-owner row no longer silently promotes that row back to admin. Correct legitimate role discrepancies through an independently authorized, audited operator action. Explicit role assignments elsewhere retain their prior behavior and require separate audit.

The shared staffing lock does not serialize external owner changes that do not acquire it. Repeatable-read transaction snapshots and changes after authorization can leave time-of-check/time-of-use windows. Test challenge races, expiry and permissions with production-equivalent MySQL and separate connections. Existing adjacent paths require separate review: owner phone OTP may bootstrap/promote an owner; staff profiles take precedence over an owner with the same email; the temporary diagnostic checks the environment owner; JWT application-ID enforcement and account-wide rate limits need separate review. Do not treat this change as a complete authentication-system security review.
